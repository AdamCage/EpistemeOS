# Изолированная проверка изменений исследовательской политики

Соберите образ из чистой рабочей копии базовой ревизии. Передайте ID локального образа службе эволюции. Рабочей копией разработчика для патча служит отдельный связанный `git worktree`.

```powershell
$baseline = git rev-parse HEAD
docker build --build-arg "BASE_COMMIT=$baseline" -f examples/evolution/Dockerfile -t episteme-evolution:baseline .
$image = docker image inspect --format '{{.Id}}' episteme-evolution:baseline
```

`DockerBackend` ожидает ID `sha256:…`. В контейнере отдельный доверенный модуль `episteme_evolution_worker` получает JSON через stdin, подставляет скопированные Python-файлы кандидата через временное дерево и возвращает один JSON-объект. Рабочая копия проекта, закрытые ответы и научное хранилище остаются на хосте. Запуск запрашивает `--network none`, read-only root, пользователя `65534:65534` и лимиты CPU, памяти, процессов, времени и захвата вывода. При отсутствии Docker или образа оценка завершается с ошибкой.

Доступные операции `evaluate` и `policy` используют одинаковый интерфейс. Поле `priorities` отображает метки доступных гипотез в объекты с полями `discrimination`, `uncertainty`, `coverage` и `invalidity_risk`. Значения лежат в диапазоне от 0 до 1. Верните такой же набор меток и полей. Контроллер проверяет ответ и самостоятельно допускает выбор. Базовая реализация возвращает входные приоритеты.

Служба сравнивает родительскую и кандидатную версии на одинаковых входах. В хостовом наборе `suite_id` и `cases` каждая запись содержит `id`, `input`, закрытый `expected` и `critical`. Продвижение возможно, если кандидат вернул правильный результат для всех критических случаев, сохранил каждый правильный ответ базовой версии и исправил хотя бы один случай. Проверка активного релиза на критическом случае, который проходит его родитель, может откатить релиз. Отдельная запись хранит предыдущую версию для уже начатых циклов.

Для оптимизации инструкций установите `epistemeos[evolution]`. Адаптер `optimize_instructions` использует GEPA для выбора среди явно заданных вариантов инструкций. Обучение и валидация проходят на раздельных наборах, их входы исключаются из последующей закрытой проверки релиза. Базовый worker позволяет проверить изменения `research_policy.py`. Для оценки влияния текстовых инструкций на модель нужен фиксированный worker, который исполняет соответствующую задачу в пределах контейнера.

`EvolutionChannel.configure` замораживает `options`, `training`, `validation`, закрытый `suite`, backend, `seed` и лимит `max_evaluations` до подачи кандидатов. Два разных подтверждённых источника сигнала с одной категорией и ключом делают активный релиз готовым к автоматической настройке. При следующем `advance()` служба сначала записывает запуск кампании, затем выполняет GEPA, проверяет кандидата на закрытом наборе и обновляет активный релиз только после допуска. Для одной конфигурации запускается одна кампания. При прерывании после записи запуска её состояние остаётся неопределённым с сохранённой историей.
