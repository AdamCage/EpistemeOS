Исправление allowlist профиля v2 после падения CI на `e71bddb`, перенесённое поверх шага 8. Job `tests (ubuntu-latest, 3.11)` (run `37212314736`) упал единственным `AssertionError` в `tests/test_execution_locked.py:300` (`test_payload_sees_only_allowlisted_variables_and_no_store_by_relative_path`): среди ключей `os.environ` payload был `LC_CTYPE`, а в записанных `environment_variables` его не было. На POSIX closure по умолчанию не наследует `LANG` и `LC_*`, процесс стартует в локали C, и CPython до пользовательского кода выполняет `setenv("LC_CTYPE", ...)` (PEP 538). Тот же вызов есть в `Python/pylifecycle.c` меток CPython 3.11.11 и 3.13.0, поэтому ячейка Ubuntu 3.13 получила бы то же лишнее имя, если бы тест в ней успел завершиться. Windows PEP 538 не выполняет. Остальные три ячейки того же run завершились `cancelled`, не успехом: в `.github/workflows/ci.yml` `fail-fast` не задан, а значение по умолчанию отменяет остальные job при первом отказе. На Windows 3.11.15 интерпретатор сам `LC_CTYPE` не вставляет. До правки тот же bootstrap, запущенный с подложенными `LC_CTYPE=C.UTF-8` и канарейкой, отдавал оба имени программе. Теперь bootstrap читает `control/payload-env.json` и заменяет `os.environ` allowlist до `runpy`. Объявленное значение сохраняется, в том числе если процесс пришёл с другим `LC_CTYPE`. Уже выбранная интерпретатором локаль не откатывается. Это по-прежнему не sandbox и не научная валидность. ## Незавершённое

Общая цель ещё не достигнута: реальные proposal tasks существуют, но независимых Executor/Replication/Scientific Reviewer provider agents, аутентифицированных назначений и контекстной/OS изоляции, полного runner с environment reconstruction/resource ledger/leases, автоматического review-driven replanning и полного manuscript pipeline пока нет. Первый trusted local runner восстанавливает результат по completion без повторного исполнения; это часть M2. M1–M6 остаются в [плане](mvp-plan.md); прототип закрывает только указанные сценарии.

Docker CLI обнаружен, но проверка `docker version` не смогла подключиться к Linux engine named pipe; повторная read-only проверка 17 сентября дала тот же результат. Sandbox на этом хосте не проверялся. Новый Windows backend использует Job Object для жизненного цикла процессов, сохраняя обычные права пользователя на файлы/сеть.

Независимый технический [review от 7 сентября](implementation-review.md) сохраняет результаты того запуска. Отмеченное там отсутствие защиты от review автором гипотезы исправлено и проверено отдельным `test_hypothesis_author_cannot_review_when_another_actor_registered_protocol`; исторический отчёт не переписан как будто исправление было проверено раньше.
