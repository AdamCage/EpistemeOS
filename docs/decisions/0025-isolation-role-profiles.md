# ADR 0025 — профили ролей изоляции

Дата: 5 октября 2026. Статус: **принято 5 октября 2026 координирующим агентом по делегированию пользователя; реализовано и проверено локально.** Пользователь делегировал проектные решения координатору. Решения ниже не переоткрываются. Числа проверки — в [validation.md](../validation.md). Основания: [архитектура](../architecture.md) (§7, §9, §11), [ADR 0019](0019-execution-profile-v2.md), [ADR 0024](0024-pack-hook-subprocess.md).

Профиль исполнения v1/v2 — это про программу и окружение uv. Этот ADR про другое: кто какой контекст получает и какая граница ОС при этом записана. Метка роли сама по себе не является этой границей.

## Проблема

Исполнитель, рецензент и репликатор уже различаются строкой `role` у актора. Это проверка разделения обязанностей в доверенном локальном процессе. Она не записывает, была ли у процесса отдельная учётная запись ОС, sandbox или запрет сети. [ADR 0024](0024-pack-hook-subprocess.md) запускает хуки пакета в subprocess того же пользователя и прямо говорит, что это не sandbox. [ADR 0019](0019-execution-profile-v2.md) описывает дерево исходников и uv-closure; контейнер там оставлен на потом, потому что на этом хосте Docker нет.

Путаница опасна в двух местах. Выдача review с ролью `reviewer` выглядит как слепой контекст, хотя провайдер под той же учётной записью может прочитать дерево реализации. Запуск в контейнере легко назвать независимой репликацией, хотя код тот же.

## Решение

1. **Три профиля роли**, и они пишутся на сам run или на выдачу review, а не только в строку актора: `executor`, `reviewer`, `replicator`. У нового run поле `role_profile` есть в payload. У новой выдачи оно есть на `review_dispatch` и копируется на `review_response`. Исторические события без этого поля остаются действительными. Отсутствие поля не считается изоляцией и не считается доказательством, что рецензент не видел реализацию.

2. **Два backend.** `local_subprocess` — значение по умолчанию и то, что есть сегодня. Записанный профиль говорит `backend=local_subprocess` и `os_isolation=none`. Там же записаны `host_user=same`, `network_enforcement=not_enforced`, `filesystem_enforcement=not_enforced`, `sandbox=false`, `independent_replication=false` и `proves_implementation_withheld=false`. Выбор метки роли на этом backend не делает review независимым и не доказывает, что у рецензента не было дерева реализации.

3. **`container` необязателен.** Запрос идёт через `isolation.execute` / `request_container`. Payload стартует как `docker run --network none --read-only --pull never` с allowlist файловых mount только для чтения. Если Docker нет, запрос отвергается до записи события и до записи blob. Тихого отката на `local_subprocess` нет. Команда `isolation.execute` с `backend=local_subprocess` тоже отвергается: локальный путь остаётся у прежних команд.

   Список mount рецензента не может содержать kind `implementation_tree`, `pack_source` или `work_directory` и не может лежать внутри деревьев, которые запрос сам назвал как implementation tree и pack source. Репликатор получает два файла, чьи digest совпадают с `inputs_digest` и `outputs_digest`, и не получает kind `work_directory`. Это правило списка mount, а не доказательство, что человек не видел код другим путём: `proves_implementation_withheld` остаётся `false`.

4. **Прежние команды остаются на `local_subprocess`.** `kernel.start_run`, execution batch, цикл исследования и выдача `review.dispatch` не получают параметр container и не переключаются на него в тестах. Отпечаток их запросов не меняется: новое поле появляется в событии, а не в аргументах старой команды.

5. **Контейнер не становится независимой репликацией.** `code_relation` равен `same_code`, если записанные digest кода совпали, `different_code`, если разошлись, и `not_compared`, если эталона не было. `independent_replication` в записи всегда `false`. Предикаты `proves_implementation_withheld` и `counts_as_independent_replication` тоже возвращают `false`: ни метка роли, ни backend контейнера не читаются как независимость или как научная валидность.

6. **Что именно проверено у контейнера.** Backend запускает свой probe до payload и верит только строкам `ROOT_READONLY` / `ROOT_WRITABLE` и `NET_BLOCKED` / `NET_OPEN` до маркера `END_PROBE`. В профиль попадают `observed_root` и `observed_network`. `os_isolation=container` значит, что payload был запущен контейнером с этими флагами, а не что появилась отдельная учётная запись ОС. `host_user` остаётся `same`: демон Docker работает от пользователя контроллера. Отдельного пользователя, Kubernetes и сетевого proxy нет. Пока probe не напечатал ограничение, поле наблюдения — `not_observed`, и это не записывается как успех.

   Повтор уже записанной команды Docker не требует: replay возвращает прежнюю квитанцию и контейнер заново не стартует. Внутри write-транзакции контейнер не запускается. Допуск сверяет, что демон отвечает, что digest названных файлов совпали с наблюдением и что текст probe согласован с полями. Второй раз контейнер при этом не стартует. Локальный вызывающий, который может положить blob в CAS, при установленном Docker может описать запуск, которого этот процесс не делал. Путь, который действительно стартует контейнер, — `request_container`.

На этом хосте Docker нет. Тест, который стартует контейнер, в обычном прогоне пропускается с явной причиной. Шаг GitHub Actions на `ubuntu-latest` с Python 3.11 делает `docker pull busybox:1.36.1` и запускает только этот тест. Сам шаг этим коммитом не исполнялся: ветка не публикуется.

Сила claim и `scientific_validity` не меняются. Golden histories не переписываются: у них нет поля `role_profile`, и проверка графа для такого события ничего не домысливает.

## Вне области

Отдельные учётные записи ОС, Kubernetes, сетевой proxy, живые вызовы модели и любое изменение силы claim. Профили исполнения `trusted_local_python_v1` и `uv_locked_python_v2` этим ADR не переписываются. Контроллер цикла по-прежнему запускает существующий local runner.

## Ход реализации

Один шаг. `role_profile.py` собирает локальный профиль, проверяет список mount и, когда Docker есть, запускает контейнер до транзакции. Новые run и новая выдача review записывают локальный профиль. `isolation.execute` записывает контейнерный профиль на run (`executor`, `replicator`) или на `review_dispatch` (`reviewer`, актор команды — planner). Историческая выдача без поля проходит replay. Graph сверяет контейнерный профиль с observation в CAS и не считает отсутствие поля изоляцией.

## Что остаётся

Контейнер — только те свойства, которые probe увидел в том запуске, который реально стартовал. Это не sandbox хоста, не отдельный пользователь и не независимая репликация. Программа профилей v1 и v2 по-прежнему может читать хранилище: это A-12, не этот ADR. Шаг Ubuntu CI в workflow есть; этот коммит его не запускал.
