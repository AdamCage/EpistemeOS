# ADR 0015 — разведочный офлайн-пилот Afterlife

Дата: 3–4 октября 2026. Статус: реализовано и локально проверено на synthetic fixture и одном историческом run; публичный CI для этого среза не запускался. Результаты проверок указаны в [validation.md](../validation.md).

## Проблема

Read-only import исторического `llm-semantic-afterlife` не создаёт исполняемый protocol или claim. После [ручной domain binding](0014-manual-domain-binding.md) общему runner нужен конкретный второй domain pack, который проверит исходные bytes, исполнит отдельные реализации анализа и остановится до научного verdict. При этом выбранные девять траекторий были увидены до нового протокола: называть повторный анализ заранее зарегистрированным исходным экспериментом нельзя.

## Решение

`compile_seed_bundle` принимает каталог одного завершённого исторического run. До записи исследовательских событий он проверяет точный инвентарь из 30 заявленных файлов, SHA-256 каждого, hash `config_resolved`, полный grid из трёх semantic и трёх stochastic seeds, а также число шагов, stop-событий, округлённую частоту, provider counts и billed token totals девяти траекторий. Каждая запись шага должна быть UTF-8 JSON без повторных ключей и нечисловых констант, ровно с восемью полями `step`, `text`, `finish_reason`, `prompt_tokens`, `completion_tokens`, `cost_usd`, `served_provider`, `from_cache`, с непрерывной нумерацией, допустимыми типами, конечной неотрицательной стоимостью и непустым provider; файл шагов ограничен 1 MiB. Любое нарушение останавливает захват до первой записи в CAS. Все заявленные исходные файлы и manifest сохраняются в CAS. Самостоятельный bounded `input.dat` содержит исходные bytes девяти `.steps.jsonl`; остальные outputs остаются CAS provenance, а не скрытым вводом для вычисления. Legacy `generated_tokens` не приравнивается к billed `completion_tokens_total`.

Пример `examples/afterlife_historical_pilot.py prepare` сначала объявляет историческую экспозицию, затем создаёт planning-bound exploratory protocol с открытым discovery split и двумя конкурирующими объяснениями **согласованности сохранённых записей**. Узел дерева поиска имеет действие `baseline` и нулевую оценку discrimination. Девять значений `--seed` в runner являются индексами уже существующих траекторий 0–8; они не обозначают новые случайные выборки. `domain.bind` фиксирует recipe, исходник адаптера и обе программы до `batch.plan`. Общий локальный runner выполняет 9 primary и 9 same-data reanalysis jobs. Primary сохраняет точные исходные step bytes в `raw.json`; отдельная программа пересчитывает долю stop-событий и возвращает идентичные raw bytes.

Предметный адаптер при `analysis advance --adapter afterlife_seed_v1` ещё раз проверяет frozen bundle, manifest, его configuration hash, метки seed grid, полный roster, записи шагов и метрики обеих программ. Строки шагов он делит по bytes так же, как захват и обе программы. Затем адаптер предлагает только `inconclusive`/`exploratory` claim. Controller назначает reviewer на текущем basis и останавливается в `awaiting_review`; reviewer verdict не создаётся. Без флага CLI использует synthetic adapter, и такая попытка отклоняется без новых событий; изменённый после `domain.bind` исходник адаптера тоже отклоняется.

## Научная и техническая граница

Этот пилот измеряет только диагностическую долю вызовов с `finish_reason` вне `null` и `length` **в данных конкретного исторического run**. Значения `finish_reason` сообщает provider. Пилот не пересчитывает исходный S1 семантический разрыв `D_between − D_within`: выбранные файлы не содержат embeddings, необходимых для этого результата. Девять траекторий происходят от одного выбранного model/configuration и были уже наблюдены. Шаги внутри траекторий не независимые экспериментальные единицы; pipeline не строит по ним p-value, interval или причинный вывод. Повторный анализ использует те же bytes и не является `new_data_replication`. Он получает `raw.json` первичной программы вместе с legacy counts, с которыми сверяется, поэтому эта сверка не слепая. Разные implementation digests не подтверждают независимого авторства: обе программы и адаптер написаны в одном локальном контексте разработки, а runner не ограничивает обычный доступ программ к файлам или сети.

Согласие сохранённых шагов с legacy manifest — предусловие захвата, а не исход эксперимента. Run с расхождением отклоняется до первого исследовательского события, поэтому конкурирующее объяснение «записи несогласованы» не может получить в этом пилоте сохранённый результат; batch повторяет уже выполненную проверку через общий runner. По этой причине claim остаётся `inconclusive`, узел дерева помечен `baseline`, а statement и limitations claim прямо называют это ограничение. Чтобы сохранять такое расхождение как отрицательный результат, нужен отдельный протокол, где сверка выполняется только после регистрации.

Legacy manifest не покрывает `events.jsonl`, `STATUS` и лог: он сохраняет целостность только своих 30 объявленных outputs. Хеши EpistemeOS фиксируют локально захваченные bytes; они не удостоверяют историческое время регистрации, отсутствие прежнего просмотра, полное восстановление исходной среды/provider или научную состоятельность. Reviewer должен отдельно оценить содержательные утверждения и ограничения. Для проверки исходного S1 результата потребуется новый доступ к embedding outputs или заранее спланированное вычисление с явно зафиксированными версиями модели, tokenizer и метрики.

Общее ядро при `analysis advance` и `batch advance` повторно проверяет все receipts на исторических префиксах. Для 18 slots это занимает порядка минуты на локальной машине; ускорение этой проверки — отдельная задача ядра, а не адаптера.
